# 寄存鉴别发货系统

## 场景
注意:本题目,仅限使用golang编程语言作答,若使用其他编程语言作答会被记为 0 分.

实现一个面向 C2B2C 二手潮品交易的后端服务。平台采取「先鉴别、后发货」模式：卖家把商品寄存到平台，由平台的鉴别师做真伪鉴定，通过的入库等待出售；买家在平台下单付款，系统自动从库存中匹配一件已鉴别通过的寄存品，由平台代发给买家。整个交易过程买家与卖家不直接交换货物，平台负责真伪保障与物流中转。

## 业务流程

### 卖货链路（卖家视角）

1. **寄存登记**：卖家挂出一笔寄存（指定商品款式 + 报价），平台还没收到实物
2. **到货确认**：实物寄达平台，平台标记为「已到货」，等待鉴别师介入
3. **鉴别**：鉴别师对实物做真伪鉴定，可能结果为「通过 / 不通过 / 疑似」。疑似的需要再由**另一位**鉴别师做二次鉴别
4. **入库等售**：鉴别通过的寄存品被分配到一个具体的物理库位存放，状态变为「待发货」，开始可被订单匹配
5. **被匹配后出库**：当有买家订单匹配到这件寄存时，系统标记寄存「已发出」，库位释放，对应的卖家结算款记入

### 买货链路（买家视角）

1. **下单**：买家选定一款商品下单（含买家信息、买家信誉级别、订单金额），状态「待付款」。系统在创建订单时**立即按 `amount × 1%` 算定 `fee` 并写入 `settle_amount = amount - fee`**——这两个字段值在订单生命周期内不再变化
2. **付款**：买家完成付款，订单进入下一阶段（直接进入「待发货」或「待匹配」，参见步骤 3）
3. **自动匹配寄存**：系统从该商品所有「待发货」状态的寄存中挑一件分配给本订单，订单状态推进至「待发货」。**高信誉买家在匹配时享有合理优先权**——即便寄存已被低信誉买家锁定但尚未发货，也可能被高信誉买家抢占
4. **发货**：平台触发发货动作，订单状态「已发出」，对应寄存与库位的状态联动更新，卖家结算款入账
5. **签收**：买家确认收货，订单状态「已签收」，结算完成

### 钱的流向

每笔订单的金额 = 平台手续费（1%）+ 卖家结算款。订单创建时由系统自动计算 `fee` 和 `settle_amount`，发货环节卖家结算款被记入；订单一旦取消则相关资金回退。simple 版不再维护独立钱包账户，资金动作直接体现为订单字段变化。

### 异常分支

- **鉴别不通过**：寄存品状态进入「鉴别不通过」，由后续物流退回卖家（simple 版只关注鉴别结果状态，不细化退回物流）；卖家累计一次违约
- **二次鉴别也不通过**：判定为假货，寄存品作废，卖家累计违约 +2
- **卖家违约累积**：违约 1-2 次降级为「警告」，≥3 次触发「封禁」——封禁会作废该卖家所有**未发出**的寄存（包括待到货/已到货/待发货等非终态），取消其作为卖方关联的**未发出**订单（详见业务规则 4）
- **取消**：寄存或订单在终态前都可主动取消
- **超时**：寄存到货超时、订单签收超时由逻辑时钟驱动自动转换（详见后文「业务规则」与「时钟模型」）

## 实体（6 类）

系统包含 6 类实体并行运转，状态机之间存在大量级联，并对外提供 REST API + WebSocket 实时推送。

### 实体字段说明

> 每个实体的字段附简短含义。**返回体里字段名是硬契约**，必须与下面完全一致。

#### Seller 卖家
把商品寄存到平台出售的用户。鉴别失败累计违约，过多触发封禁。

| 字段 | 含义 |
|---|---|
| `id` | 卖家唯一标识，前缀 `sl_` |
| `nickname` | 昵称（创建时由用户传入）|
| `status` | 账号状态：`正常` / `警告` / `封禁` |
| `violation_count` | 违约累计次数（鉴别不通过 +1，假货确认 +2）|
| `credit` | 信用分。**simple 版始终保持初始值 100，不随业务变化**（仅作为展示字段保留供后续扩展）|

#### Identifier 鉴别师
平台员工，对到货商品做真伪鉴定。

| 字段 | 含义 |
|---|---|
| `id` | 鉴别师唯一标识，前缀 `id_` |
| `name` | 鉴别师姓名 |
| `status` | 工作状态：`在岗` / `休息` / `停职` |
| `daily_quota` | 当日处理量上限（创建时可指定，未传则默认 100）|
| `today_processed` | 当日已处理任务数（系统自动累计，跨日重置）|
| `shift_end` | 下班时间（**逻辑时钟绝对分钟数**，与 `GET /system/time` 返回的 `minutes` 同基准；当前时钟 ≥ 此值则该鉴别师自动转休息，不再接单）。**创建时不传**为 `null`，表示无下班时间限制 |

#### Product 商品 SKU
商品款式定义，同款不同卖家可有多条寄存。

| 字段 | 含义 |
|---|---|
| `id` | 商品唯一标识，前缀 `p_` |
| `name` | 商品名 |
| `sku` | 商品 SKU 编码 |
| `category` | 品类：`鞋` / `包` / `表` / `其他`（决定库位区域）|
| `status` | 上架状态：`在售` / `下架` / `已删除` |
| `stock` | 平台当前持有的鉴别通过未发货件数（鉴别通过 +1、发货 -1，由系统维护）。**包含**已被订单匹配但未发货的件数（即库位「锁定」状态的件也计入 `stock`），订单 ship 时才减 1 |

#### Consignment 寄存单
卖家挂的一笔具体寄存（卖家 + 商品 + 报价），是核心业务对象。

| 字段 | 含义 |
|---|---|
| `id` | 寄存单标识，前缀 `c_` |
| `seller_id` | 所属卖家 |
| `product_id` | 所属商品 SKU |
| `asking_price` | 卖家报价（浮点）|
| `status` | 当前状态（见下方状态枚举）|
| `slot_id` | 入库后绑定的库位 ID，未入库为 null |
| `arrived_at` | 实际到货时刻（逻辑分钟数）|
| `outbound_at` | 出库时刻 |
| `priority` | 优先级（创建时可指定；**simple 版当前不参与匹配逻辑**，作为字段保留供后续扩展）|
| `created_at` | 创建时刻 |

**鉴别相关字段**（系统在鉴别接口被调用后自动写入，不接受外部直接写）：

| 字段 | 含义 |
|---|---|
| `identify_round` | **已完成**的鉴别轮次数：`0`(未鉴别) / `1`(一次完成) / `2`(二次完成) |
| `identify_round1_id` | 一次鉴别的鉴别师 ID |
| `identify_round1_result` | 一次结果：`通过` / `不通过` / `疑似` |
| `identify_round1_at` | 一次鉴别完成时刻 |
| `identify_round2_id` | 二次鉴别的鉴别师 ID（**合规要求与一次不同**）|
| `identify_round2_result` | 二次结果 |
| `identify_round2_at` | 二次鉴别完成时刻 |

#### Slot 库位
平台仓库的物理存储格位，鉴别通过的寄存品占用一个库位。

| 字段 | 含义 |
|---|---|
| `id` | 库位标识，前缀 `s_` |
| `code` | 库位编号（创建时传入，如 `A-01-03`）|
| `status` | 状态：`空闲` / `已占用`（鉴别通过后入库时分配）/ `锁定`（被订单匹配后到发货前）/ `损坏`。库位仅在 Consignment 鉴别通过、状态进入 `待发货` 时才被分配；`二次鉴别中` 等中间态**不预占库位** |
| `current_consignment_id` | 当前存放的寄存单 ID，空闲时为 null |
| `zone` | 所属区域：`A` / `B` / `C`（决定能存哪类商品）|

#### Order 订单
买家下单意向，付款后系统自动匹配寄存品再发货给买家。

| 字段 | 含义 |
|---|---|
| `id` | 订单标识，前缀 `o_` |
| `product_id` | 下单的商品 SKU |
| `buyer` | 买家标识符（字符串，不是独立实体；**与 WebSocket 通道 `/ws/buyer/{buyer_id}` 中的 `{buyer_id}` 为同一值**）|
| `buyer_credit` | 买家信誉级别：`金` / `银` / `铜` |
| `amount` | 订单总金额（浮点，由买家下单时指定，**与卖家寄存的 `asking_price` 无关联**——买家可任意定价，系统不强制 `amount ≥ asking_price`，匹配寄存时也不参考价格高低）|
| `fee` | 平台手续费 = `amount × 1%`（系统自动算）|
| `settle_amount` | 卖家结算款 = `amount - fee`（系统自动算）|
| `status` | 订单状态（见下方）|
| `consignment_id` | 匹配上的寄存单 ID，未匹配为 null |
| `paid_at` | 付款时刻（逻辑分钟，付款后写入）|
| `outbound_at` | 发货时刻（逻辑分钟，调用 `/ship` 时写入；签收超时 7 天从此时刻起算）|
| `received_at` | 签收时刻（逻辑分钟，调用 `/receive` 时写入；自动签收时也写入）|
| `cancel_reason` | 取消原因（若已取消）|

> `fee` 与 `settle_amount` 在创建订单时由系统按 `amount` 一次性算定并写入，**整个订单生命周期内值不变**；状态机推进表达的是履约阶段，而非金额变化。卖家"结算款记入"是从该卖家维度统计已成交订单（`已发出` / `已签收` / `已结算`）的 `settle_amount` 之和，而非某个时刻的资金转账动作。

**ID 前缀汇总**：Seller `sl_xxx` / Identifier `id_xxx` / Product `p_xxx` / Consignment `c_xxx` / Slot `s_xxx` / Order `o_xxx`

## 状态枚举

- **Seller**：正常 / 警告 / 封禁
- **Identifier**：在岗 / 休息 / 停职
- **Product**：在售 / 下架 / 已删除
- **Consignment**：待到货 → 已到货 → `鉴别通过` / `鉴别不通过` / `鉴别疑似`（提交鉴别结果时直接到达，标答跳过短暂 `鉴别中` 中间态——选手实现时进与不进均可）；`鉴别通过` → 待发货 → 已发出（终态）；`鉴别不通过`（终态）；`鉴别疑似` → 二次鉴别中 → 回流到 `鉴别通过` 或 `已作废`；任意非终态可主动 `已作废`。注：`鉴别中` / `退回中` / `已退回` 三个状态保留在枚举中供未来扩展，simple 版不会出现
- **Slot**：空闲 / 已占用 / 锁定 / 损坏
- **Order**：待付款 → 待发货（付款成功且匹配到寄存）或 待匹配（付款成功但暂无可用寄存）→ 已发出 → 已签收（终态，调用 `/receive` 或超时 7 天自动达到，simple 版即代表订单履约完成）；任意非「已发出」之后的状态可主动 `已取消`。
   注：状态枚举集合中保留 `已付款` 和 `已结算` 仅供描述完整性，标答在接口返回后已推进，**不会在 API 响应中出现** `已付款` 也不会出现 `已结算`；选手实现是否保留 `已付款` 短暂状态自行决定。

## 接口约定

所有接口走 REST，请求/返回体均为 JSON，返回体含实体完整字段。

**幂等性**：所有 POST/PUT 接口接受 `Idempotency-Key` 请求头；幂等去重**按 `(method, path, key)` 三元组隔离**——同一个 key 用于不同接口路径互不影响。5 分钟内同三元组重复调用返回首次结果。

每个接口标注**调用者**与**功能**。「调用者」并非鉴权校验，而是说明真实业务中谁会触发该操作；技术上接口对所有客户端开放。

### 卖家（运营人员管理）

| 接口 | 调用者 | 功能 |
|---|---|---|
| `POST /sellers {nickname}` | 运营 | 入驻新卖家，初始 `正常` / `violation_count=0` / `credit=100` |
| `GET /sellers` / `GET /sellers/{id}` | 运营 | 查询卖家列表 / 详情 |
| `GET /sellers/{id}/stats` | 运营 | 查询卖家统计信息。返回 `{total_orders, total_revenue, violation_rate, recent_30d_orders, avg_settle_minutes}`：`total_orders` 是该卖家所有寄存单数；`total_revenue` 是已完成订单（`已发出` / `已签收` / `已结算`）的 `settle_amount` 求和；`violation_rate = violation_count / total_orders`，当 `total_orders = 0` 时返回 `0` |

### 鉴别师（人事 + 鉴别师本人）

| 接口 | 调用者 | 功能 |
|---|---|---|
| `POST /identifiers {name, daily_quota?}` | 人事 | 入职新鉴别师，初始 `在岗`，`daily_quota` 未传则默认 100 |
| `GET /identifiers` / `GET /identifiers/{id}` | 任意 | 查询列表 / 详情 |
| `PUT /identifiers/{id}/shift-end {minutes}` | 人事 | 设置下班时间（绝对分钟数）|
| `POST /identifiers/{id}/rest` | 鉴别师本人 | 主动休息（状态转 `休息`，不再接单）|
| `POST /identifiers/{id}/resume` | 鉴别师本人 | 从休息恢复（状态转 `在岗`，可接单）|
| `PUT /identifiers/{id}/suspend` | 人事 | 停职（终态，不可恢复）|

### 商品（运营人员管理）

| 接口 | 调用者 | 功能 |
|---|---|---|
| `POST /products {name, sku, category}` | 运营 | 新建商品 SKU，初始 `在售`、`stock=0` |
| `GET /products` / `GET /products/{id}` | 任意 | 查询列表 / 详情 |
| `PUT /products/{id}/status {status}` | 运营 | 上下架（仅 `在售` ↔ `下架` 互转）；商品已 `已删除` 后**不可恢复**（HTTP 400）|
| `DELETE /products/{id}` | 运营 | 软删除（状态置 `已删除`，终态）|
| `GET /products/{id}/consignments?status=待发货&sort=asking_price` | 内部撮合 | 列出商品下符合 `status` 的寄存。`sort=asking_price` 按报价**升序**排序（同价按 `arrived_at` 升序兜底）；不传 `sort` 不保证顺序 |

### 库位（仓管员管理）

| 接口 | 调用者 | 功能 |
|---|---|---|
| `POST /slots {code, zone}` | 仓管 | 登记新库位，初始 `空闲` |
| `GET /slots` / `GET /slots/{id}` | 任意 | 查询列表 / 详情 |
| `POST /slots/{id}/report-damage` | 仓管 | 报损（状态转 `损坏`，不可分配）|
| `POST /slots/{id}/repair` | 仓管 | 修复（损坏 → 空闲）|

### 寄存单（卖家提交 + 鉴别师提交鉴别）

| 接口 | 调用者 | 功能 |
|---|---|---|
| `POST /consignments {seller_id, product_id, asking_price, priority?}` | 卖家 | 创建寄存单，初始 `待到货` |
| `GET /consignments` / `GET /consignments/{id}` | 任意 | 查询列表 / 详情 |
| `POST /consignments/{id}/arrive` | 平台收货员 | 标记到货（`待到货 → 已到货`，同时写入 `arrived_at = 当前逻辑时钟`）|
| `POST /consignments/{id}/identify {identifier_id, result, fail_reason?}` | **鉴别师** | 提交鉴别结果，**核心接口**（详见下方）|
| `POST /consignments/{id}/cancel {reason?}` | 卖家或运营 | 主动取消（仅非终态可取消）|

**`identify` 接口详解**：

- `result` 取值：`通过` / `不通过` / `疑似`
- 系统根据 `identify_round` 自动识别第几轮：
  - `identify_round=0` 且 status=`已到货` → 一次鉴别（写 round1 字段，identify_round 升至 1）
  - `identify_round=1` 且 `identify_round1_result=疑似` → 二次鉴别（写 round2 字段，identify_round 升至 2）
  - 其他状态调用应拒绝（HTTP 400）
- **二次鉴别合规**：`identifier_id` 必须与一次的不同（HTTP 400）
- **状态自动转换**（提交结果后系统立即推进 `status`）：
  - 一次 `通过` → `待发货`（同时分配 Slot + `Product.stock+1` + 自动匹配待匹配 Order）
  - 一次 `不通过` → `鉴别不通过`（卖家 `violation_count+1`，后续退货物流不涉及本系统）
  - 一次 `疑似` → `二次鉴别中`（等待不同鉴别师二次鉴别）
  - 二次 `通过` → `待发货`
  - 二次 `不通过` → `已作废`（假货，卖家 `violation_count+2`）
  - 二次 `疑似` → `已作废`（**不增加**卖家违约次数）

### 订单（买家下单 + 平台运营）

| 接口 | 调用者 | 功能 |
|---|---|---|
| `POST /orders {product_id, buyer, buyer_credit, amount}` | 买家 | 下单，初始 `待付款`，系统自动算 `fee` 和 `settle_amount` |
| `GET /orders` / `GET /orders/{id}` | 任意 | 查询列表 / 详情 |
| `POST /orders/{id}/pay` | 买家 | 付款（待付款 → 已付款 → **同步匹配寄存**；接口返回时已确定结果：匹配上则 `status=待发货` 且 `consignment_id` 已填，未匹配则 `status=待匹配` 且 `consignment_id=null`）|
| `POST /orders/{id}/ship` | 平台仓管 | 触发发货（订单 `待发货 → 已发出`，写入 `Order.outbound_at`；**同时**更新关联寄存为 `已发出` 并写入 `Consignment.outbound_at`；释放对应 Slot 为 `空闲`；`Product.stock -1`）|
| `POST /orders/{id}/receive` | 买家 | 手动签收（`已发出` → `已签收`，同时写入 `received_at`；`已签收` 即终态）|
| `POST /orders/{id}/cancel {reason?}` | 买家或运营 | 取消订单。仅当订单状态为 `待付款` / `已付款` / `待匹配` / `待发货` 时可取消；状态 `已发出` 起（含已签收/已结算）不可取消（HTTP 400）|

## 业务规则

### 显形规则

1. **手续费**：每笔订单平台收取手续费 = `amount × 1%`（保留至浮点），卖家结算金额 = `amount - fee`。
2. **寄存到货超时 48 小时**：`待到货` 寄存单从 `created_at` 起若 48 小时仍未到货，自动转 `已作废`。
3. **签收超时 7 天**：订单状态为 `已发出` 且 `outbound_at + 7×24×60 分钟` 已到，未手动签收的自动转 `已签收`（同时写入 `received_at = 当前逻辑时钟`）。
4. **卖家违约级联**：
   - 鉴别不通过 → 卖家 `violation_count +1`；二次鉴别确认假货 → `+2`
   - `violation_count ∈ {1, 2}` → Seller `警告`
   - `violation_count ≥ 3` → Seller `封禁`（终态）
   - 封禁影响范围：
     - 该卖家**未发出**的寄存单 → `已作废`；其关联的**未发出**订单 → `已取消`
     - **已发出（含已签收）的订单**不受影响，正常走完签收/结算流程
     - 「关联订单」指该卖家作为**寄存卖方**关联的订单（非该卖家作为买家身份的订单）
     - 封禁后该卖家不能再新建寄存单（`POST /consignments` 返回 HTTP 400）
5. **库存自增**：商品的 `stock` 字段由系统自动维护（鉴别通过 +1、发货 -1），不可手动修改。
6. **订单匹配**：订单付款后系统**同步**从该 product 的 `待发货` 寄存池中挑选一个绑定到本订单，订单转 `待发货`；若池中无可用寄存，订单进入 `待匹配`，等待新寄存通过鉴别后再触发匹配。
7. **订单取消的级联**：订单在 `待发货` 状态被取消时，关联的库位状态从 `锁定` 回 `已占用`（库位 `current_consignment_id` 保留指向原寄存单，Consignment 状态保持 `待发货`），该寄存单可被其它订单重新匹配。**被取消订单的 `consignment_id` 字段保留**（记录历史匹配关系，不清空为 null）。`待付款` / `已付款` / `待匹配` 状态的订单取消不涉及寄存联动。
8. **商品下架/删除的边界**：`PUT /products/{id}/status {status:下架}` 和 `DELETE /products/{id}` 仅改商品自身 `status`，**不级联**已存的寄存单和订单（待发货寄存品、待匹配/待发货订单、已发出订单均按原流程继续走完，付款/发货/签收等动作不受影响）。下架/删除只影响**新的**业务动作：
   - 不能再为该商品**新建订单**（创建时返回 HTTP 400）
   - 不能再为该商品**新建寄存单**（创建时返回 HTTP 400）

### 实时推送语义

- **派发推送**：当 Consignment 进入鉴别流程并被分配给某个鉴别师时，向该鉴别师订阅频道推送 `task_assigned` 事件。
- **状态变更推送**：Consignment / Order 状态变更后，分别向卖家 / 买家订阅频道推送相应的 `*_status_changed` 事件。
- **风控事件推送**：卖家被警告 / 被封禁时推送 `warned` / `banned` 事件。

## 业务提示

- 同款商品可能有多个寄存单同时进入 `待发货` 状态，系统在匹配订单时**应符合买家利益**地选择寄存单。
- 鉴别师有工作量限制，**请合理派单**避免某个鉴别师超负荷。
- 鉴别 `疑似` 结果需走二次鉴别流程，**二次鉴别师必须与一次不同**（合规去重）。
- 不同品类的商品需要存储在**不同的物理区域**（库位有区域属性），分配库位时需要遵循这种物理隔离要求。
- 高信誉买家在订单匹配中享有**合理的优先权**，平台需要在不影响已发货订单的前提下给予其优先体验。

## 时钟模型

系统使用逻辑时钟，单位为分钟。**服务首次启动时初始值为 `0`**；`POST /system/tick {minutes}` 推进时钟并触发所有时间敏感的自动评估（到货超时、签收超时、跨日重置等）。`GET /system/time` 返回当前时钟 `{minutes: N}`。
