# 可观测性三件套：Metrics / Logging / Tracing

## 开篇：为什么不能只依赖云厂商监控？
很多人觉得阿里云、腾讯云自带监控面板，CPU、内存、磁盘都能看，没必要自己搭监控。这个认知在单体服务时代勉强成立，但在多服务部署、K8s 容器化的场景里完全站不住脚。

核心问题很现实：一台服务器上跑十几个服务，单个服务报错、延迟飙升，很容易被整体均值「中和」掉，云监控大盘看起来一切平稳，实则某个核心链路已经炸了。再加上容器化部署后，需要监控到 Pod 粒度的状态，云厂商的基础监控覆盖不到这么细的维度。

线上故障发现越晚，损失越大，最后兜底排查、担责任的还是开发自己。Metrics、Logging、Tracing 这三样东西，本质不是什么高大上的技术炫技，是线上系统的「保命三件套」，分工不同，配合起来覆盖从预警到根因定位的全流程。

---

## 一、Metrics（指标）：系统的「体检仪表盘」
### 核心本质
用**可聚合的数值**定量描述系统的运行状态，按时间周期持续采集，用来宏观判断系统健不健康、有没有过载。
它不关心单个请求的细节，只看整体统计结果，是做告警、提前发现异常的核心手段。

### 核心监控两类指标
- 基础设施层：CPU 使用率、内存占用、磁盘剩余、网络带宽、Redis/数据库连接数
- 业务服务层：接口 QPS（每秒请求量）、平均/分位响应耗时、错误率、消息队列积压量

### 主流实现方案
- **Prometheus**：时序型数据库（TSDB），主动定时拉取业务暴露的指标数据，支持 PromQL 语法查询；可以配置告警规则，指标超过阈值时自动推送通知。
- **Grafana**：可视化仪表盘工具，对接 Prometheus 等数据源，把数值绘制成折线图、热力图等监控大盘，是行业通用的展示方案。
- 进阶玩法：可以把指标数据喂给大模型做智能分析，把结论推到钉钉、飞书，不用天天盯着大盘。

### 我的个人判断 
1.  **业务指标远比机器指标重要**。CPU 满了不一定服务不可用，但接口错误率涨到 10% 一定是出问题了。新手容易沉迷盯机器负载，忽略了真正影响用户的业务指标。
2.  **指标不是加得越多越好**。乱加自定义指标会导致「指标爆炸」，时序库存储压力陡增，查询变慢，最后得不偿失。只盯核心指标就够了。
3.  **告警宁少勿滥**。什么阈值都设告警，最后会陷入告警风暴，大家都麻木了，真出问题反而没人看。

## 二、Logging（日志）：故障排查的「现场证据」
### 核心本质
程序运行过程中打印的事件记录，是最基础、也是最常用的观测手段。它可以携带丰富的上下文信息，是出问题后定位根因的最终依据。

### 日志里该记录什么
- 错误异常与完整堆栈信息
- 请求 ID、用户 ID、订单号等业务唯一标识
- 关键函数的入参、出参
- 第三方调用、SQL 执行的关键信息

示例（Go 伪代码）：
```go
if err != nil {
    hlog.Warn("创建订单失败", 
        "userId", 10086, 
        "orderId", "OD20260622", 
        "err", err)
    return err
}
```

### 我的个人判断 
1.  **落地优先级最高，没有之一**。小团队刚起步，哪怕什么监控都没有，也要先把日志打规范。出了问题至少有地方可查，不至于两眼一抹黑。
2.  **不带唯一标识的日志，等于白打**。尤其是微服务场景，日志里不加 request_id、订单号，出了问题海量日志里根本搜不到对应的那条，排查效率为零。
3.  **控制 Info 级日志的量级**。什么都打 info 日志，会导致日志量爆炸，存储成本高，查错也慢。只在关键节点打日志，错误日志一定要打全。

## 三、Tracing（分布式追踪）：微服务的「全链路CT」
### 核心本质
专门为分布式/微服务架构设计的观测技术。给每一次前端请求分配一个全局唯一的 `TraceID`，跟着请求穿透所有服务，记录每一段调用的耗时、状态、错误信息，最终还原出完整的调用链路。
它解决的核心痛点是：跨服务的请求，到底哪一环慢了、哪一环报错了，不用挨个服务去翻日志。

### 举个最常见的例子
支付请求链路：前端 → API 网关 → 订单服务 → 库存服务 → 支付服务
- **性能问题排查**：用户反馈支付很慢。不用挨个服务去看日志，直接找一条慢请求的 TraceID，就能一眼看到库存服务数据库查询花了 2s，是整个链路的瓶颈。
- **故障定位**：支付失败但没有明确报错。通过 TraceID 直接定位到异常出在支付服务，附带当时的调用上下文，快速锁定根因，不用跨服务甩锅。

### 我的个人判断 
1.  **服务少于 5 个别急着上，性价比极低**。单体服务或者两三个服务的场景，日志加 request_id 完全够用，上链路追踪纯属于增加运维成本。
2.  **它不替代日志，是日志的串联索引**。真正排查细节还是要靠日志，Tracing 的价值是帮你快速定位到「哪个服务、哪个时间段」出问题，然后精准去捞日志。
3.  **最大的价值是省时间**。以前跨服务排错要登好几台机器搜日志，现在一个 TraceID 直接定位环节，排错效率提升几倍。

## 四、三者核心对比
| 类型 | 核心定位 | 数据形态 | 解决的核心问题 | 主要短板 | 代表工具 | 落地优先级 | 性价比 |
|------|----------|----------|----------------|----------|----------|------------|--------|
| Metrics 指标 | 宏观监控、异常预警 | 聚合数值 | 系统整体是不是出问题了？有没有变慢/报错？ | 定位不到单条请求的具体原因 | Prometheus + Grafana | 第二 | 高 |
| Logging 日志 | 根因排查、现场还原 | 文本+自定义字段 | 这次报错的具体原因、上下文是什么？ | 微服务下跨服务排查效率极低 | ELK、Loki | 第一 | 极高 |
| Tracing 追踪 | 全链路定位、瓶颈分析 | TraceID + 分段调用数据 | 请求经过了哪些服务？哪里慢、哪里炸了？ | 不适合做全局宏观统计 | Jaeger、SkyWalking | 第三 | 服务少时低，服务多时高 |

## 五、线上排错的标准流程
正常的线上故障排查，一定是三者配合着用，顺序不能乱：
1.  **Metrics 先发现异常**：监控大盘告警，支付接口错误率飙升、平均耗时突增，先知道「出事了」。
2.  **Tracing 定位环节**：抽取几条异常请求的 TraceID，快速定位到故障出在库存服务，知道「哪一环出事了」。
3.  **Logging 深挖根因**：去库存服务按 TraceID 检索对应日志，看到具体的错误堆栈和 SQL 语句，确认是索引失效导致查询超时，找到「为什么出事了」。

---

## 六、落地路线

1.  **阶段一：基础打底（任何体量都适用）**
    统一日志规范，所有服务透传 request_id；错误日志必须带业务标识和完整堆栈。这一步成本最低，收益最大。
2.  **阶段二：监控告警（有线上流量就该做）**
    接入 Prometheus + Grafana，先覆盖核心接口的 QPS、响应耗时、错误率三大指标；配置核心告警，确保异常能及时通知到人。
3.  **阶段三：链路优化（微服务数量≥5再考虑）**
    接入分布式追踪系统，用 TraceID 串联全链路日志；重点优化慢调用链路，提升整体性能。

---

## 总结
- Metrics 是火警报警器，先告诉你哪里着火了
- Logging 是现场勘查，最后查明白为什么着火
- Tracing 是消防导航，直接带你找到着火的具体房间
